# rig.yaml declares its format, and Rig upgrades older formats in place

For [#309](https://github.com/b-relay/rig/issues/309), the maintainer decided that Rig reads more than one rig.yaml format at once, so a change to how config is spelled, such as [#282](https://github.com/b-relay/rig/issues/282) moving `ready` into a `health` block, does not break existing Projects. This amends [ADR 0001](0001-yaml-only-project-config-cutover.md): config stays YAML only, but Rig now has a migration command, `rig config upgrade`, for moving a `rig.yaml` between its own formats. It never reads another file format.

- A top-level `format` names the format a file is written in. The name `version` was rejected because it reads like the application's or Rig's version. A file without `format` is `rig/v1`, the format of every rig.yaml written before this, so every existing file keeps working unchanged. `rig init`, `rig config upgrade` and `rig recipe generate` write the latest format, `rig/v2`.
- Each format is validated by its own schema, so a mistake is reported at the path the author wrote. The parser then moves an older file to the latest format's shape and validates that again. Everything after the parser (planning, the runtime, status, doctor, recipes' comparisons) sees one shape and never branches on the format; the parsed config carries no `format`, and the document records the one it was written in. A recorded Target plan is made from that one shape, so a file's format cannot change a plan: upgrading a file is not config drift. (#302 showed what an unexpected plan difference costs.) The Working copy's own drift note compares a digest of the parsed config, so an upgrade, or a comment, is not drift there either; a Target recorded by an older rigd is still compared by the file's text.
- The formats are a list of steps. A step names the Service settings it moves; parsing an older file, refusing an older name in a newer file, `rig config upgrade`, printing a recipe in an older format and naming a field in `rig recipe diff` all read that one list. `rig/v2` is one step: a Service's `ready` and `ready_timeout` become `health.check` and `health.start_timeout`, in Services and in every role's Service patch, and a `${...}` reference to one of them follows it. In `rig/v2` the old names are refused with where they moved; in `rig/v1` a `health` block is refused with a pointer to the upgrade. An unknown `format` is refused: it needs a newer Rig.
- Every `rig` command run in a Project whose rig.yaml is an older format prints one deprecation line naming `rig config upgrade`. rigd adds it to the reply of any command that read such a file, including a deploy of a Commit whose committed rig.yaml is older, which still deploys; `rig` and `git-remote-rig` print it once on stderr, `git push --quiet` included. `rig recipe generate`, which reads only the nearby file's `format` and needs no rigd, prints it itself.
- `rig config upgrade` rewrites rig.yaml in place and prints each change; `--dry-run` prints a unified diff and writes nothing. It edits the file's text only where the format change needs to, located through the parsed YAML tree, so comments, order, quoting (of keys too), blank lines, flow style and long lines stay byte for byte; a reference the source spells with an escape is written again as a double-quoted string, a yaml-language-server comment naming the older schema is pointed at the current one, and a comment the move would drop from inside a flow mapping makes it refuse. The config editor's re-rendering of the whole tree was not used because it rewrites flow collections (`[api]` becomes `[ api ]`) and would touch lines the upgrade has no reason to. Before writing, the result must parse, in the latest format, to exactly the config the file had; otherwise nothing is written. The write is the config editor's: rigd takes the Project's config scope, the file lock and revision check, and keeps `rig.yaml.bak`. It changes only the working tree: nothing is committed, planned or restarted, and it is a config edit, not Activity.
- JSON Schema: `schemas/rig.schema.json` describes the latest format and requires `format`. Each older format keeps a frozen schema of its own, `schemas/rig-v1.schema.json`, marked deprecated, which a file not yet upgraded may point its editor at. One combined schema with a condition on `format` was rejected because editors complete and explain conditional schemas poorly.
- The dashboard's config editor edits a file in its own format's spelling and shows the deprecation notice.

A format is removed only by a later decision; until then Rig reads it.
