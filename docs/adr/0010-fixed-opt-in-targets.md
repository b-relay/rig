# Targets have fixed names and are off unless rig.yaml turns them on

This supersedes [ADR 0006](0006-target-roles-and-configurable-names.md). The owner is making rig.yaml feel like Docker Compose or Process Compose, with sensible defaults, and this is the first of three steps. ADR 0006 let rig.yaml rename the Working copy and Stable Targets (`local` and `live` by default) and ran every role a Project could deploy. In practice that gave one Target several names (`local`, `dev`, the role key `working`), a rename rule with its own errors (`TARGET_AMBIGUOUS`, a recorded name that kept selecting until the next plan), and a Stable Target or Preview anyone could deploy whether the Project meant to have one or not.

- **Fixed names.** The Targets are `working`, `stable` and `preview`. These are the names in rig.yaml, on the command line, in status and output, in the dashboard and in the domain language; the kinds `local` and `live` are gone too. `targets.<role>.name` is refused with "Target names are fixed (working, stable, preview); delete this line." Previews keep their generated names (`<branch slug>-<8 hex>`), or the one `--deployment` gives; a new Preview cannot be named `working`, `stable` or `dev`.
- **Off unless switched on.** A Target is on when its key under `targets` is `true` or a settings map (the existing patch fields); `false` or a missing key is off. A rig.yaml with no `targets` key at all has only `working` on, so a new Project runs its checkout and deploys nothing. `up`, `restart`, `deploy` and `logs` of a never-run Target refuse an off Target with `TARGET_OFF`, whose hint names the line to add, so nothing of it is planned, published or started. Status and the dashboard list only the Targets that are on, and any Target that is off but still recorded, so a config change never strands a running process: it can be seen, read, stopped and destroyed. Turning a Target off does not stop it.
- **CLI defaults.** In a checkout `rig up`, `rig down`, `rig restart` and `rig logs` without a Target mean `working`, and `rig deploy` means `stable`; `rig deploy preview <branch>` stays. A Preview is never a default. The interactive Target picker is gone.
- **Tool names.** The stable Target publishes a Tool under its plain name, the working Target as `<tool>-dev` (a short fixed suffix, because `working` is too long to type), and a Preview as `<tool>-<preview name>`.
- **Flat Preview hostnames.** A Preview's default hostname is the Project domain with a dash and the Preview name after its first label: `pantry2.dev.b-relay.com` and `feat-x-1a2b3c4d` give `pantry2-feat-x-1a2b3c4d.dev.b-relay.com`, a sibling of the domain rather than a subdomain of it. `targets.preview.domain` still overrides it. A label longer than DNS's 63 characters is refused when the Preview is planned, with a hint, and is never cut short.
- **Existing state.** Runtime state moves to version 5. rigd reads version 4, written when Targets were `local`, `live` or a renamed name such as `dev`, by giving each working or stable record its role as kind and name, as `readRetiredSupervisorAsRigd` and `forgetOngoingHealthChecks` normalize older records; the next write saves it so. Recorded domains and routes stay as they were served; routes are keyed by the Target's id, so the next plan replaces them. A working Target's Tool published as `<tool>-<old name>` is recorded as `publishedAs`, so status still finds it and the next plan retires it beside the new `<tool>-dev`. Activity keeps the old names as the text it recorded. A Preview that already holds a role's name keeps it, and that Target keeps its old name until the Preview is destroyed.

Why: one vocabulary instead of a name and a role for the same thing, a simpler rig.yaml with nothing to rename, and nothing that deploys by surprise.
