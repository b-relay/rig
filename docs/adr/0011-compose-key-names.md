# rig.yaml uses Compose names and shorter references

The owner is making rig.yaml feel like Docker Compose or Process Compose, with sensible defaults; [ADR 0010](0010-fixed-opt-in-targets.md) was the first step and this is the second. A rig.yaml written for Rig should read like a Compose file to anyone who has written one, and moving a Project to Compose later should be mostly a copy. Rig's own names for the same settings (`run`, `env`) were one more thing to learn, and every port was spelled `${services.<name>.ports.<port>}`, even inside the Service that declares it and in a `proxy` whose Service has one port.

- **Compose names where the meaning matches.** A Service's `run` is `command`, and `env` is `environment` at Project level, in a Service and in every Target patch (still a map of `KEY: value`). `env_file`, `depends_on`, `ports`, `restart` and `build` already had Compose's names and keep them. References follow the settings: `${environment.NAME}` and `${services.<name>.environment.NAME}`. The old keys and the old `env.` reference paths are refused with a hint naming the new name, as ADR 0009 refused `format` and `health`; there is no format version and no automatic rewrite (ADR 0009's rule).
- **`working_dir`** (the Compose and Process Compose name) is the directory a Service's `command`, its `build` and a shell `ready` check run in, relative to the workspace and patchable per Target. It cannot leave the workspace: absolute paths, `~`, `..` and references are refused. The default is the workspace root, as before. `env_file` paths and `${rig.workspace}` still mean the workspace root.
- **Short port references.** In a Service's own settings `${port}` is its only port and `${ports.<name>}` one of its named ports; anywhere references are allowed `${services.<name>.port}` is that Service's only port. A Service with no port or several is refused where `${port}` asks for one, with what to write instead. A Project-level value or a Project or Tool build has no Service, so `${port}` there is refused too. The long form `${services.<name>.ports.<port>}` keeps working.
- **`proxy` may name a Service** (`/api: api`) for its only port; the long form still works. When `proxy` is left out, `/` is the one Service that declares ports, when that Service declares exactly one: a Target with a hostname routes to it, and without a hostname `${rig.url}` is its local address, as with an explicit proxy. A Target that is on, has a hostname and has no usable proxy is refused with what to add.
- **`build: false`** in a Target patch, for the Project build or a Service's, turns the inherited build off for that role. At the top level, where leaving the key out already means no build, it is refused.
- **Recorded state.** Plans keep their internal shape (`command`, `env`), so nothing in them is renamed except the config paths a plan records as the sources of its command inputs (`env.NAME` becomes `environment.NAME`), which are read under the new name so such a plan equals today's plan. A Working copy planned by a rigd before this change recorded a digest of its rig.yaml under the old names; renaming the keys of an unchanged file is not reported as drift, because the digest is also compared with the file spelled the old way.
- **Deployed revisions are not rewritten.** A stable Target or Preview deployed from a Commit whose rig.yaml uses the old names keeps running its recorded plan, but that rig.yaml no longer parses. `rig doctor` reports it as `config-predates-rename` rather than as an invalid config whose fix would be an edit, and names the deploy that clears it. Deploying, or rolling back to, a Commit whose rig.yaml uses the old names is refused until its rig.yaml is updated; there is no reader for the old names.

[ADR 0005](0005-services-use-platform-independent-inputs.md) still holds. `${port}` is still an explicit mapping written in rig.yaml from a Rig-generated value to an input the application defines, such as `PORT: ${port}` or `--port ${port}`; it is shorter, not implicit. Rig sets no variable the configuration does not name, and the default route only decides which Service a hostname reaches, not what the application reads.
