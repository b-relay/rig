# A Service's health check is Docker Compose's healthcheck

The owner is making rig.yaml feel like Docker Compose or Process Compose, with sensible defaults; [ADR 0010](0010-fixed-opt-in-targets.md) and [ADR 0011](0011-compose-key-names.md) were the first two steps and this is the third. A Service's start check was Rig's own `ready` (a URL or a command) and `ready_timeout`, and nothing checked a Service once it had started: [ADR 0009](0009-one-project-config-format.md) removed the ongoing checks #317 had added under a `health` block, with their alerts, to cut Rig down. Anyone who has written a Compose file already knows `healthcheck`, and moving a Project to Compose later should not mean rewriting its checks. This decision brings ongoing checks back, in Compose's shape.

- **`healthcheck` replaces `ready` and `ready_timeout`**, in a Service and in every Target patch, with Compose's keys and meanings: `test`, `interval` (default 30s, at least 5s), `timeout` (default 30s), `retries` (default 3), `start_period` and `disable`. `test` is a string, which is a shell command, or Compose's `["CMD-SHELL", "<command>"]`, `["CMD", "<program>", "<argument>", ...]` (run without a shell; Rig quotes each argument whole) or `["NONE"]`. References work as they did in `ready`, `${port}` included. `ready` and `ready_timeout` are refused with where each moved, as ADR 0011 refused `run` and `env`, and the hint for #317's `health` block now names `healthcheck`. `rig init --ready` became `--healthcheck`.
- **Two extensions.** A string `test` that starts with `http://` or `https://` is an HTTP GET that must answer below 400 without following a redirect and must address `127.0.0.1` or `localhost`, exactly as a `ready` URL did; Compose has no such form, and a `curl` in every rig.yaml would be noise. A string starting with `/` is a command (an executable path), as in Compose, never a path on the port. `on_failure` is Rig's one new key: `report` (the default, and Compose's only behaviour) or `restart`.
- **`start_period` defaults to 30s, not Compose's 0s.** In Compose, start_period is a grace in which failures do not count. In Rig the first passing check is the start gate: `up`, a deploy and a restart wait for it (checking every 100 ms, not at `interval`), and `depends_on` waits for it, as `ready` did. A 0s budget would fail every start, so the default keeps `ready_timeout`'s 30s, and the guide says so.
- **Ongoing checks run whenever a Service has a healthcheck**, as in Compose; there is no separate switch. The passing start check is the first passing check, so a started Service is healthy at once; `rigd` checks again every `interval`, and checks a process it did not see start (one that survived a `rigd` restart) as soon as it sees it running with the Target free. After `retries` failures in a row it is unhealthy; one pass makes it healthy again; Activity records both with the check's last output cut to 200 characters. Checks pause while an Operation holds or waits for the Target, never overlap for one Service, and at most four run at once on the Host. `rig status`, the dashboard and `rig doctor` read the cached result and run nothing. There are no alerts.
- **`on_failure: restart`** stops an unhealthy Service through the normal stop path (its `stop_timeout`, under its Target's lock or queue) and starts it again, at once and then after 1m, 5m, 15m and every hour while it stays unhealthy. Health restarts spend none of the crash-restart budget. A health restart whose start fails its start check stays the health monitor's: the Service stays stopped and unhealthy and is started again at the next step of the back-off, whatever its `restart` policy, so Rig never gives up on it; an explicit start ends that, and `rig down` stops it. A Host restart holds such a working Target or Preview stopped until `rig up`, and rigd starts a stable one as it starts every stable Target after a Host restart. Only a replacement confirmed stopped waits for the next health restart; one whose rollback failed is checked as the running process. #317's `retry_for`, which gave up after a while, is not brought back: an hourly restart is cheap, and giving up was one more state to explain.
- **Without a healthcheck nothing changes**: a start waits for every declared port to accept a connection, and nothing is checked afterwards. `disable: true` and `["NONE"]` mean exactly that too, which is how a Target patch drops an inherited healthcheck. A healthcheck without `test` checks the declared ports, as the start gate does without one; on a Service with no port it is refused.
- **Recorded state.** A plan keeps `health` (the resolved test) and `readyTimeout` (now start_period) and gains `healthcheck` (interval, timeout, retries, on_failure). A plan recorded before this change has no `healthcheck`, so it keeps meaning a start check only: a running Target needs no restart, nothing checks it, and status runs its start check as before. A Service without `ready` plans exactly what it did, so it shows no drift. Moving `ready` to `healthcheck` does change what the Target does, so it is drift until the Target is planned again; no digest trick hides it. The unhealthy stretch a health restart continues is recorded on the Service's run as `healthStretch`, so a new `rigd` keeps the back-off, and an explicit start clears it. #317's own recorded fields (`healthMonitor`, `healthRestarts`) are still dropped when state is read.

This restores ongoing checks that ADR 0009 removed, under a new name and shape; ADR 0009's one-format rule stands.
