# Scheduled jobs run in rigd, from a Target's plan

The owner is moving everything off Dokploy onto this Mac. Melody needs cron-style batch jobs (a link resolver every six hours, a nightly palettes backfill, a twice-weekly MusicBrainz mirror that runs for hours, a catalog ETL), and backups will later be built the same way. Rig had only Services, which it keeps running, and Tools, which it installs; a job is neither.

- **`jobs:` in rig.yaml**, beside `services:`, keyed by name. A job has a Service's Compose names (`command`, `environment`, `env_file`, `working_dir`, `stop_timeout`) plus `schedule` (a standard five-field cron expression), `timezone`, `timeout` and `targets`. It cannot share its name with a Service or Tool: logs, status and `rig logs --service` name all three alike. A Project may consist of jobs alone. Target patches cannot change jobs.
- **Target scope.** A job is planned into a Target like a Service, from the same checkout (the working copy, or a deployment's Commit) and with the same references: `${services.<name>.port}` and `.ports.<p>` reach the Target's Services, `${rig.data}` is the job's own persistent directory (`<data root>/<job>`), and `${services.<name>.data}`, new here, is a Service's persistent directory, so Melody's jobs share the `api` Service's cover cache and mirror directory. `${services.<name>.data}` works in a Service too, and is refused, as a Service's environment is, in a Project or Tool build. A job has no port of its own, so `${port}` is refused in it.
- **Targets decide scheduling only.** The schedule runs a job in the stable Target only, unless its `targets` list names `working`, `stable` and/or `preview` (every Preview), ADR 0010's fixed names. Every Target plans every job (a job its `targets` do not name is planned with `scheduled: false`), so `rig run <job> <target>` runs it in any Target that is on and deployed, such as `working` to try a stable-only job. A Target runs its jobs on schedule only while it is deployed (no unfinished deploy or transition), meant to run (not `rig down`) and on in rig.yaml; `rig run` needs the same, since rigd's first pass after a restart stops the runs of a Target meant to be stopped.
- **Time zone.** `timezone` is a validated IANA name; without it the schedule is read in the Mac's own zone as rigd reads it (status shows the zone in use; after changing the Mac's zone, a rigd restart may be needed for rigd to see it). Daylight saving time has one rule: a wall time the spring change skips (02:30 when 02:00 jumps to 03:00) runs once, at the change; a wall time the autumn change repeats runs once, the first time. A daily job runs exactly once on both days. `UTC` never shifts.
- **The scheduler lives in rigd** behind a clock interface (`JobClock`) and the process supervisor, so tests drive it with a fake clock. A pass every second hands the latest due time of each job to an Operation on its Target, which waits for the Target like any command, checks it is still meant to run the job, records the run, then starts it through the same capture wrapper as a Service (key `<target id>:job:<name>`, output in the Target log under the job's name). The run is recorded before its process starts. **The scheduler changes nothing itself**: it only reads state and observes processes. Recording a run's end, stopping it at its timeout, and giving back a checkout are Operations on the Target too, which read the run again under the Target's lease and act only when the record still names the run the scheduler judged, and only on a process carrying that run's incarnation; a run started after the scheduler looked (say by `rig run`, once the run before it exited) is never stopped or recorded in its place.
- **No overlap.** A time that comes due while the previous run still goes is skipped: the first skip of a run is one Activity entry, later ones are counted on the run. `rig run <job>` while a run goes is refused with `JOB_RUNNING`.
- **Missed times are not caught up, and nothing is recorded for them.** A due time may start up to 5 minutes late (a busy Target, a rigd restart); a later one, as after the Mac slept or rigd was down, is dropped silently, and only the latest time within those 5 minutes runs. Status shows the last and next run, which tells the story. The latest time acted on is recorded (`lastScheduled`), times passed over included (by a stopped Target, by one rig.yaml turned off, or because the Target was busy past the late limit), each recorded under the Target's lease, so a new rigd never runs a time twice or one a stopped Target let pass; when rigd first sees a job it records that (`watchedFrom`), so a time due between then and a restart within the 5 minutes still runs, even before the job's first run.
- **Deploys never cut a run off.** A deploy stops the previous plan's Services but not its job runs. A run finishes on the checkout it started in; the deploy keeps that checkout (a run in progress references it), the next run uses the new deployment, and when the run ends rigd gives the old checkout back. A deploy whose new plan drops the job still lets the run end. `rig restart` leaves runs alone too. `rig run` needs a Target meant to run, and a Project with a run in progress cannot be renamed, repointed or forgotten. `rig down`, a Preview destroy, rigd's first pass finding a Target meant to be stopped, and rig.yaml turning the Target's role off (checked every 10 seconds while a run goes; an exception to ADR 0010's "turning a Target off does not stop it") stop a run within the `stop_timeout` it started with, recorded as stopped by Rig; a job that cannot be stopped never keeps `rig down` from stopping the Services. `timeout` stops a run the same way, recorded as timed out (a run that had already ended keeps its own exit). A stop Rig cannot confirm (the process still runs, cannot be inspected, or does not carry the run's incarnation, which is never signalled) fails `JOB_STOP_UNVERIFIED`: `rig down` still stops the Services and then reports it, and a Preview destroy is refused before anything of the Preview changes, so its storage is never deleted under a run. The decision and its cause are recorded on the run before the stop signal, so a rigd that restarts before recording the end still records it as stopped or timed out. A checkout a run kept is recorded in the same write as the run's end and offered back every 30 seconds until it is gone, by this rigd or the next, so neither a crash nor a failed removal leaks it. A run whose job a deploy dropped stays in status (as removed, unscheduled) and in `rig logs --service <job>` until it ends.
- **rigd restarts.** Stopping rigd leaves a run going under its capture wrapper, which records the exit; the next rigd adopts it by lease (as it adopts Services), never starts it again, and records how it ended. A Host restart ends it; the next rigd records it as ended with no recorded exit (`unknown`).
- **Records.** Runtime state moves to version 6: a plan gains `jobs`, and a new top-level `jobs` list holds, per Target and job, the run in progress, the last run (trigger, scheduled time, start, end, outcome, exit code or signal, skipped count, its checkout and limits, and a stop decision), `lastScheduled` and `watchedFrom`; a top-level `jobCheckouts` list holds the checkouts waiting to be given back. Job records live apart from Target records, so an Operation that saves its Target never overwrites them. Version 5 is read unchanged and saved as 6; an older rigd refuses version 6 rather than keep jobs it would never run. Each ended run is one Activity entry (`job`, outcome `succeeded`, `failed`, or `stopped`, its id the run's), and `rig run` is an Operation of its own whose id is the run's. Status (and so the protocol the dashboard reads) reports each job's schedule, zone, state, whether it is scheduled and why not, its next run, the run in progress and the last run. The run record is the reusable unit backups will build on.

Why: jobs are part of a Project's runtime like its Services, so they belong in rig.yaml, in a Target's plan and under rigd's authority, with the same checkout, references, logs and Activity. The rules that need an owner's judgment (default Target, missed times, DST, what stops a run) are each one rule with no special case.
