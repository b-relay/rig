# Backups are scheduled jobs with retention

ADR 0013 built scheduled jobs so backups could be built the same way. Melody's Postgres needs a nightly dump that survives deploys, is pruned to a fixed count, and can be restored with one command. Rig must not learn what a database is: the owner already knows `pg_dump` and `pg_restore`, and a preset per database would be one more thing to keep current.

- **`backup:` on a job.** A job with `backup: { keep, restore }` is a backup job. `keep` (1 to 1000, required) is how many successful backups Rig keeps. `restore` (optional) is the command that puts one back. Both commands are the job's: the same references, `environment`, `env_file`, `working_dir`, schedule, `targets`, `timeout` and `stop_timeout`. There are no presets: Rig never knows what it is backing up.
- **A fresh directory per run.** Every run of a backup job (scheduled, or `rig run`) gets a new, empty directory `<RIG_ROOT>/backups/<project>/<target>/<job>/<id>/`, mode 0700, where `<id>` is the run's start in UTC (`20261011T030000Z`, with `-2`, `-3` when a second starts in the same second). The command sees it as `$RIG_BACKUP_DIR`, which rigd sets after the env files, so no file can change it. The run records the directory before the directory is made and before the process starts, so a rigd that stops at any step finds it.
- **Failed runs leave nothing.** A run that ends any way but exit 0 (a failed exit, a timeout, a stop by Rig, a start that failed, or an end nothing recorded) has its directory deleted. A successful one becomes a backup: its directory is made read-only (directories 0500, files lose their write bits, each changed through a descriptor opened without following symlinks; a symlink, and a file with another hard link such as a live database, are left as they are, so sealing never changes anything outside the backup), and its size recorded. A run that exits 0 but deleted its directory or replaced it with a symlink keeps no backup (`lost`) and evicts none. A backup a rigd stopped before sealing is sealed and measured on the next 30-second pass.
- **Retention after success only.** In the same state write that records a successful run, Rig keeps the newest `keep` backups of that job in that Target, the one that just finished always among them, and queues the rest for deletion. A failed run never deletes a backup. `keep` is the value the run started with, as `timeout` is.
- **Deletion is recorded before it happens.** A backup leaving the inventory, and a failed run's directory, go to `backupRemovals` in the same write; rigd deletes the directory (making it writable first, never following a symlink, refusing anything outside `<RIG_ROOT>/backups`) and then forgets the entry. One it cannot delete stays queued and is offered again every 30 seconds, by this rigd or the next. Empty parent directories are removed up to `backups/`.
- **Rig never deletes what it did not record.** Directories under `backups/` that no record names (copied in by hand, or left by an older rigd) are never touched.
- **Restore is a run of the job.** `rig backup restore <job> <backup-id|latest> [target]` starts the job's `restore` command once, as a run of the job (`trigger: restore`), from the Target's plan: the Target's checkout, references, env files and working directory, under the job's process key and in its logs. `$RIG_BACKUP_DIR` is the chosen backup, made read-only again before the start. Being a run, a restore never overlaps a run of the job or another restore (`JOB_RUNNING` either way, and a scheduled time while it goes is skipped), `rig down` and a Preview destroy stop it, `timeout` applies, and a rigd restart adopts it. A restore run creates no backup and never changes the inventory.
- **What restore asks and records.** The CLI resolves `latest` to an id, shows the backup, and asks for confirmation unless given `--yes` (a terminal without a prompt is refused with that hint); it then waits for the run to end and exits 1 unless it succeeded (Ctrl-C stops waiting; the restore goes on). The Operation is an Activity entry `restore` (`started`, naming the backup), and the run's end another (`succeeded`, `failed` or `stopped`). A job without `restore` is refused with `BACKUP_NO_RESTORE`; an unknown id with `BACKUP_UNKNOWN`, naming the ones there are; a backup whose directory is gone with `BACKUP_MISSING`.
- **Restore does not stop Services.** The restore command is responsible for what it replaces (`pg_restore --clean --if-exists`, say). Rig neither stops nor restarts the Target's Services around it.
- **Read-only, as far as file modes go.** Sealing a backup is a file-mode change by the same user the command runs as, so it stops accidental writes (a restore that writes a temporary file next to the dump fails loudly) but a command that `chmod`s it back could still write. The directory is never moved, so its path stays stable for `list`.
- **Lifetime.** Backups live under `<RIG_ROOT>/backups`, outside every Target's data root and checkout, so deploys, `rig down`/`rig up`, `rig restart` and rigd restarts never touch them. Destroying a Preview, or the Preview limit replacing one, deletes that Preview's backups with its storage. `rig forget` keeps a Project's backups on disk, drops their records (no command could reach them) and names the directory in its warning. A job removed from rig.yaml keeps its backups, listed but no longer restorable. Backups stay on the Mac; nothing copies them elsewhere.
- **Records.** Runtime state moves to version 7: a plan job gains `backup` (`keep` and the resolved `restore`), a run gains `backup` (its directory, id and `keep`) or `restore` (the backup it reads), and two top-level lists hold the backups (`backups`: Target, job, id, path, the run it came from, its trigger, start, end and size) and the directories waiting to be deleted (`backupRemovals`). Version 6 is read unchanged and saved as 7; an older rigd refuses version 7 rather than run backup jobs without their directory.
- **Status and protocol.** Each backup job in status carries `backup`: `keep`, whether it has a `restore`, how many backups there are, their total size and the newest one. A new read, `backups`, lists them (filtered by job and Target) with their path, size and run, and whether the directory is missing; a new mutation, `restore`, takes the job, the backup id and the Target. The dashboard's Jobs tab lists each backup job's backups and offers Back up now and a Restore that asks for the job's name to be typed.

Why: a backup is "run this command on a schedule, keep the output, and be able to put it back". Jobs already give the first part with the same environment and lifecycle as Services; retention and a restore that is itself a run add the rest without Rig learning anything about Postgres or SQLite. Keeping deletions in the state before they happen means a crash never strands a directory and never deletes one Rig did not create.

Not decided here (to confirm): deleting a Preview's backups with the Preview (the conservative default, as its data goes too); whether restore should stop named Services first (`stop: [services]`); a `rig backup delete`; restoring a backup into another Target; and copies off the Mac.
