# Backups are scheduled jobs with retention

ADR 0013 built scheduled jobs so backups could be built the same way. Melody's Postgres needs a nightly dump that survives deploys, is pruned to a fixed count, and can be restored with one command. Rig must not learn what a database is: the owner already knows `pg_dump` and `pg_restore`, and a preset per database would be one more thing to keep current.

- **`backup:` on a job.** A job with `backup: { keep, restore }` is a backup job. `keep` (1 to 1000, required) is how many successful backups Rig keeps. `restore` (optional) is the command that puts one back. Both commands are the job's: the same references, `environment`, `env_file`, `working_dir`, schedule, `targets`, `timeout` and `stop_timeout`. There are no presets: Rig never knows what it is backing up.
- **A fresh directory per run.** Every run of a backup job (scheduled, or `rig run`) gets a new, empty directory `<RIG_ROOT>/backups/<project>/<target>/<job>/<id>/`, mode 0700, where `<id>` is the run's start in UTC and the next number of the backup directory's sequence (`20261011T030000Z-17`). The number is allocated in the state write that records the run, before the directory is made, and the sequence only ever grows: it is kept per `<project>/<target>/<job>` by name in `backupSequences`, never reset when backups are deleted, a Preview is destroyed or a Project forgotten, so a Preview made again under the same name or a Project registered again continues it; it also starts past every number the Target's kept backups carry, so a renamed Project never repeats one. Names that differ only in case share one sequence, since they name one directory on the Mac's case-insensitive disk: two Projects `melody` and `Melody` whose runs start in the same second still get different paths. An id is therefore never issued twice. Earlier drafts reused ids: numbering a second backup of one second `-2` gave a later run of that second the id of a deleted backup, and a tag from the run's id clashed when run ids started alike; either way a restore by an old id read a different backup. `latest` names the newest, and newest means the highest number, which the run and then the backup record as `sequence`: the sequence follows the order the job's runs were recorded, so a clock set back or forward never makes `latest`, retention or a list prefer older data. Times are shown, never used to order. A backup an older Rig recorded has no `sequence`, and the number in its id cannot stand in for one (the first writer numbered only backups made within one second): it is older than every backup that has one, and those are ordered among themselves by their place in `backups`, which adds each backup as its run ends. An id that names no kept backup is refused (`BACKUP_UNKNOWN`, or `BACKUP_EXPIRED` when the restore's own settlement let it go), never matched to another. The command sees it as `$RIG_BACKUP_DIR`, which rigd sets after the env files, so no file can change it. The run records the directory before the directory is made and before the process starts, so a rigd that stops at any step finds it.
- **Failed runs leave nothing.** A run that ends any way but exit 0 (a failed exit, a timeout, a stop by Rig, a start that failed, or an end nothing recorded) has its directory deleted, if the run made it. The directory is made exclusively and recorded as made (`made`) in a second write, before the process starts. A directory already at the path fails the start and stays; one a rigd that stopped between the two writes left (before making it, after making it, or after finding something there) cannot be shown to be the run's, so it stays too, and the run's summary says it was left in place. At worst that leaves an empty directory under a number never issued again. A run's summary says its directory was queued for deletion, as the deletion comes after the write that records the end. A successful one becomes a backup and its size is recorded, from `lstat` alone: nothing in a backup is ever opened (a FIFO left there cannot hang rigd). A run that exits 0 but deleted its directory or replaced it with a symlink keeps no backup (`lost`) and evicts none. A backup a rigd stopped before measuring is measured on the next 30-second pass.
- **No modes change.** Backup directories stay mode 0700 under the private backups root, as the run left them; Rig makes nothing read-only. An earlier draft sealed kept backups read-only as a guard against mistakes, but changing modes reached files outside a backup through hard links, stalled on FIFOs, and still could not stop a command running as the same user; the guard was not worth it. Its backups (and a directory a job made unwritable) still have to be deletable: when a deletion fails, Rig gives the owner back read, write and search on each real directory inside the backup that the user owns, found by `lstat` without following a symlink, and deletes again. No file's mode changes, so nothing reached through a hard link does. Before each attempt every directory in the backup is checked to be on the backup root's volume: a backup with another volume mounted inside it (one a job left mounted, say) is not deleted at all, so nothing on that volume is touched; it stays queued with a hint to unmount it, and goes on the first pass after.
- **Retention after success only.** In the same state write that records a successful run, Rig keeps the newest `keep` backups of that job in that Target (by `sequence`), the one that just finished always among them, and queues the rest for deletion. A failed run never deletes a backup. `keep` is the value the run started with, as `timeout` is.
- **Deletion is recorded before it happens.** A backup leaving the inventory, and a failed run's directory, go to `backupRemovals` in the same write; rigd deletes the directory (never following a symlink, refusing anything outside `<RIG_ROOT>/backups`) and then forgets the entry. One it cannot delete stays queued and is offered again every 30 seconds, by this rigd or the next. Empty parent directories are removed up to `backups/`.
- **Rig never deletes what it did not record, nor through a symlink.** Directories under `backups/` that no record names (copied in by hand, or left by an older rigd) are never touched. Containment is checked on disk, not only by path: every directory between `<RIG_ROOT>/backups` (which may itself be a symlink) and a backup must be a real directory. A backup below a symlinked one is not created (`BACKUP_PATH`, so its run fails to start), reads as missing, and is skipped when its deletion comes due (forgotten with a diagnostic, nothing deleted). A race by another process running as the same user between that check and the deletion is out of scope.
- **Restore is a run of the job.** `rig backup restore <job> <backup-id|latest> [target]` starts the job's `restore` command once, as a run of the job (`trigger: restore`), from the Target's plan: the Target's checkout, references, env files and working directory, under the job's process key and in its logs. `$RIG_BACKUP_DIR` is the chosen backup. Before choosing it, the restore settles a run of the job that ended but is not recorded yet, under its hold on the Target, so that run's retention can never delete the backup it then reads; an id chosen beforehand that this retention let go is refused with `BACKUP_EXPIRED`. Being a run, a restore never overlaps a run of the job or another restore (`JOB_RUNNING` either way, and a scheduled time while it goes is skipped), `rig down` and a Preview destroy stop it, `timeout` applies, and a rigd restart adopts it. A restore run creates no backup and never changes the inventory.
- **What restore asks and records.** The CLI resolves `latest` to an id, shows the backup, and asks for confirmation unless given `--yes` (a terminal without a prompt is refused with that hint); it then waits for the run to end and exits 1 unless it succeeded (Ctrl-C stops waiting; the restore goes on). The Operation is an Activity entry `restore` (`started`, naming the backup), and the run's end another (`succeeded`, `failed` or `stopped`). A job without `restore` is refused with `BACKUP_NO_RESTORE`; an unknown id with `BACKUP_UNKNOWN`, naming the ones there are; a backup whose directory is gone with `BACKUP_MISSING`.
- **Restore does not stop Services.** The restore command is responsible for what it replaces (`pg_restore --clean --if-exists`, say). Rig neither stops nor restarts the Target's Services around it.
- **Lifetime.** Backups live under `<RIG_ROOT>/backups`, outside every Target's data root and checkout, so deploys, `rig down`/`rig up`, `rig restart` and rigd restarts never touch them. Destroying a Preview, or the Preview limit replacing one, deletes that Preview's backups with its storage. `rig forget` keeps a Project's backups on disk, drops their records (no command could reach them) and names the directory in its warning. A job removed from rig.yaml keeps its backups, listed but no longer restorable. Backups stay on the Mac; nothing copies them elsewhere.
- **Records.** Runtime state moves to version 7: a plan job gains `backup` (`keep` and the resolved `restore`), a run gains `backup` (its directory, id and `keep`, and later `made` once the run made the directory) or `restore` (the backup it reads), and three top-level lists hold the backup numbers issued (`backupSequences`), the backups (`backups`: Target, job, id, path, the run it came from, its trigger, start, end and size) and the directories waiting to be deleted (`backupRemovals`). Version 6 is read unchanged and saved as 7; an older rigd refuses version 7 rather than run backup jobs without their directory.
- **Status and protocol.** Each backup job in status carries `backup`: `keep`, whether it has a `restore`, how many backups there are, their total size and the newest one. A new read, `backups`, lists them (filtered by job and Target) with their path, size and run, and whether the directory is missing; a new mutation, `restore`, takes the job, the backup id and the Target. The dashboard's Jobs tab lists each backup job's backups and offers Back up now and a Restore that asks for the job's name to be typed; the dashboard's server checks what was typed in a restore action of its own, and its generic command action refuses `restore`, so no page script can skip the confirmation.

Why: a backup is "run this command on a schedule, keep the output, and be able to put it back". Jobs already give the first part with the same environment and lifecycle as Services; retention and a restore that is itself a run add the rest without Rig learning anything about Postgres or SQLite. Keeping deletions in the state before they happen means a crash never strands a directory and never deletes one Rig did not create.

Not decided here (to confirm): deleting a Preview's backups with the Preview (the conservative default, as its data goes too); whether restore should stop named Services first (`stop: [services]`); a `rig backup delete`; restoring a backup into another Target; and copies off the Mac.
