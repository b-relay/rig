# Rig manages the owner's DNS records, through rigd, with the proxy's token

The owner asked to manage the DNS records of `b-relay.com` from the dashboard's Proxy page. [ADR 0014](0014-rig-owned-caddy.md) settled that "Rig manages no DNS records": Caddy's DNS-01 challenge was the token's only use. But the token `rig proxy token` stores already holds Zone:Zone:Read and Zone:DNS:Edit on the zone, every hostname Rig serves needs a record that points at this Mac, and the Cloudflare dashboard is one more place to keep in step by hand. This ADR reverses that one bullet of ADR 0014 and nothing else of it.

## Decision

- **Same credential, no new one.** rigd reads `<RIG_ROOT>/auth/acme-dns.token` for each DNS request (`src/adapters/dns-token.ts`, checked like doctor's `proxy-token`: present, the user's, mode 600, well formed) and drops it after. The token never crosses the control plane, never reaches the browser, and is never logged, recorded or quoted: every failure the provider raises passes through `redactSecrets` with the token as a secret, and a redirect is never followed, so the token goes nowhere but Cloudflare.
- **Provider behind an interface.** `DnsProvider` (`src/providers/contracts.ts`) speaks Rig's terms: list zones, list a zone's records, read one, create, update, delete (update and delete say when the record no longer existed). `proxy.tls.dns` names the provider and rigd's composition picks it from a registry; `cloudflare` is the only one, as for certificates. `createCloudflareDns` (`src/providers/cloudflare-dns.ts`) implements it against API v4: `GET /zones` and `GET /zones/:id/dns_records` read every page (`page`, `per_page`, `result_info.total_pages`, or a short page), at most 100 pages; `POST`, `PATCH` and `DELETE` on `/zones/:id/dns_records/:id` write, with Bearer auth. Each request has a 10-second deadline that covers its body; every answer is validated with Zod; ids that are not short alphanumerics never reach a URL; CNAME and MX targets are read lowercase. Failures are tagged: `DNS_AUTH` (401/403), `DNS_RATE_LIMIT` (429), `DNS_PROVIDER` (a refusal, with Cloudflare's own reason), `DNS_PROVIDER_RESPONSE` (an answer Rig does not understand, or a redirect: not the owner's to fix, so not user-correctable), `DNS_TIMEOUT`, `DNS_UNREACHABLE`.
- **Zones.** Every zone the token can see. Host config may narrow it with `proxy.dns.zones: [example.com]`; a listed zone the token cannot see is reported. Each zone's records are read on its own, four at a time: a zone the token cannot read, or a rate limit on one, is reported (`unreadableZones`) beside the zones that were read, and the hostnames in it are `unknown`. Only when no zone can be read does the read fail, with that reason. For this Host that is `b-relay.com` either way.
- **Record types.** A, AAAA, CNAME, TXT, MX and CAA, each with name, content, TTL (1 for automatic, or 30 to 86400 s), `proxied` (A, AAAA and CNAME only), `priority` (MX only, and required) and `comment` (up to 500 characters). The TTL floor and the comment limit are the widest Cloudflare allows on any plan (30 s on Enterprise, else 60; 500 characters on paid plans, else 100), so an edit never fails on a value Cloudflare already stored; Cloudflare refuses a narrower plan's excess with its own reason. Content rules per type: IPv4, IPv6, a hostname for CNAME and MX (not the record's own name), printable TXT up to 2048 characters, CAA as `<flags> <tag> "<value>"` (sent to Cloudflare as structured `data`). Names are lowercase labels of letters, digits, `-` and `_`, the first label optionally `*`, inside the zone. Other types in a zone (NS, SRV, HTTPS…) are listed read-only.
- **TXT quoting.** Cloudflare documents TXT content as RFC 1035 quoted character-strings of up to 255 bytes, splits a longer value into several (`"part1" "part2"`), and returns content as stored, quoted or not. Rig compares TXT values as a resolver assembles them (`txtValue`: the strings joined, `\"`, `\\` and `\DDD` unescaped), so `"v=spf1 -all"` and `v=spf1 -all` are one value. Rig sends TXT content as typed. This was checked against Cloudflare's documentation only, never the live API.
- **Protocol.** Four actions on `/v1/command`, so the CLI and the dashboard share one path, its admission and its Activity:
  - `dns` (read): zones, every record, this Mac's address, and the hostname check. Optional `dns.zone` narrows it.
  - `dns-create`, `dns-update`, `dns-delete` (mutations) with `dns: { zone, record?, id?, modifiedOn?, absent?, confirm? }`. The record's content rules are checked in rigd, so a mistyped address is `DNS_RECORD` naming the field, not an invalid request.
  - Writes to one zone hold a lock scope of their own (`["dns", zone]`), beside every Project and Target, so a DNS change never waits for a deploy and two changes of one zone run one at a time.
  - A rigd built without DNS answers `DNS_UNAVAILABLE`, apart from a Host without a proxy section (`DNS_UNCONFIGURED`).
- **Concurrency.** Cloudflare offers no conditional write (no ETag or If-Match on DNS records). So every update and delete carries the record's `modifiedOn` as the caller read it; rigd reads the record again just before writing and refuses with `DNS_CHANGED` when it is gone or its `modified_on` differs, and a write Cloudflare answers with "no such record" (removed in between) is `DNS_CHANGED` too. A create that expects the name to be free (`absent`) is refused the same way when a record of its type, or a CNAME, appeared meanwhile; Point at this Mac, `rig dns set` of a type the name had none of, and the dashboard's Add of a name and type the page showed none of all send it. The window left is one round trip to Cloudflare; an edit there inside it wins silently, and Rig's next read shows it.
- **Deletes are confirmed by name, in rigd.** `dns-delete` requires `confirm`, the record's full name as the person typed it; rigd compares it (any case, a trailing dot allowed) with the record it reads just before deleting and refuses `DNS_CONFIRMATION` on a mismatch. So no client can skip the typed confirmation. The CLI sends the name after its own prompt or `--yes`; the dashboard sends what was typed through a Server Action of its own (`runDnsDelete`), and its generic `runCommand` refuses `dns-delete`, as #337 does for restores.
- **Lost answers.** A write whose answer times out, never arrives, or is cut off partway through its body may have been made. rigd reads the record back: a create whose record is there, an update whose record now says everything that was asked (content, TTL, proxying, MX priority, and a comment when the change carried one; content compared as Cloudflare normalizes it: hostnames lowercase, TXT assembled, IPv6 in RFC 5952 form, CAA by flags, tag and unquoted value), and a delete whose record is gone are reported, and recorded, as done. Only a complete body that is not JSON is `DNS_PROVIDER_RESPONSE`. A write that is plainly not made stays the failure it was; when even the read-back fails, the write fails `DNS_UNCERTAIN`, saying to read the records before retrying.
- **Activity.** Every write is an Operation recorded in Activity with its record (`create A app.example.com -> 100.64.0.7`, `update A web.example.com -> 203.0.113.5 (renamed from app.example.com, was 198.51.100.1)`, `delete TXT _dmarc.example.com`), outcome `updated` or `failed` with the error code, provider failures before the write (a rate limit, a refused token) included. Never the token. A request that is the caller's own mistake or stale (`DNS_RECORD`, `DNS_CHANGED`, `DNS_REQUEST`, `DNS_ZONE`) is refused before anything is written and, like other commands' usage mistakes, goes to the diagnostic log only.
- **Hostname check.** For every hostname Rig serves (each recorded Target's sites, so Service domains once [ADR 0015](0015-service-domains.md) lands, and `proxy.routes`), rigd resolves it against the provider's records the way the zone's authoritative server would (RFC 4592): the name's own records; nothing if it exists only as the parent of other names (an `_acme-challenge` record makes its parent such a name); otherwise the wildcard at its closest existing ancestor. A name at or below an NS delegation under the apex is answered by other nameservers, so it is `unknown` with no fix. CNAMEs are followed inside the managed zones, up to 8 hops; each hop is answered by the longest zone that holds its name, read or not, so a CNAME into a child zone that could not be read is `unknown`, never answered by a parent's wildcard. The verdict:
  - `mac`: every A record that answers is this Mac's address and none is proxied. **A name covered only by a wildcard counts as pointing here when the wildcard does**, and the UI says so ("Covered only by the wildcard *.b-relay.com, which points at this Mac").
  - `elsewhere`: another address, only AAAA records, or proxied (Cloudflare's edge cannot reach a Tailscale address).
  - `missing`: no address answers.
  - `unknown`: no managed zone holds it, its zone could not be read, it is delegated, a CNAME leaves the managed zones, or this Mac's address is unknown.
- **This Mac's address** is `proxy.dns.address` when Host config sets it (an IPv4 address other machines can reach: not unspecified, loopback, link-local, multicast or broadcast), otherwise the Tailscale IPv4 from `tailscale ip -4` behind the `HostAddress` interface (tried on PATH, Homebrew and the App Store app's paths, since launchd gives rigd a short PATH). Only IPv4 is checked; AAAA records are noted, not judged.
- **Point at this Mac** is one change, planned by the check and shown before it is pressed: the name's one A record rewritten to this Mac's address, unproxied, keeping its TTL and comment; or, when the name has no A record, a new one (TTL automatic, comment "Points at this Mac; created by Rig"), which takes precedence over a wildcard that points elsewhere. Adding a record is one click; rewriting one that exists asks first. A CNAME at the name, or several A records, offer no one-click change and say what to edit instead.
- **CLI.** `rig dns list [zone]`, `rig dns set <name> <type> <content> [--ttl] [--proxied|--no-proxied] [--priority] [--comment] [--add|--replace] [--zone]` and `rig dns delete <name> <type> [--content] [--zone]`, each with `--help` and `-h`.
  - **Names.** A one-label name (`app`, `_dmarc`) is relative to the zone when there is one zone, and `@` is the apex. A dotted name must end in a managed zone; otherwise it is refused (`www.other.org` would else become `www.other.org.example.com`), and `--zone` makes any name relative to that zone.
  - **`set`.** A record of that name and type with the same content is changed in place (or left, if nothing differs). For A, AAAA and CNAME the one record is replaced, several are `DNS_AMBIGUOUS`, and `--add` adds another. TXT, MX and CAA, which a name commonly holds several of, add a record unless `--replace` changes the one there. A new record beside a CNAME, or a new CNAME beside any record, is refused before rigd is asked (`DNS_CONFLICT`).
  - **Confirmation.** Writes show the change and ask, unless `--yes`; without a terminal `--yes` is required (`DNS_CONFIRMATION`). The command plans against a fresh `dns` read and sends what it read, so the concurrency check covers the time spent at the prompt.
- **Dashboard.** A DNS section on the Proxy page: the hostname check with a Point at this Mac button per name, then each zone's records with a filter, Add and Edit dialogs (the type is fixed once a record exists) and a Delete dialog that needs the record's full name typed. Rows stack on a phone and become columns from `md` up, in the design language of #335. A zone that could not be read is named above the rest.
- **Comments cannot be cleared from Rig.** An update without a comment leaves Cloudflare's as it is (whether Cloudflare's `PATCH` clears a comment sent as `""` or `null` is not documented clearly enough to rely on). The Edit dialog says so beside the field.
- **Not set up.** Without a `proxy` section the commands fail `DNS_UNCONFIGURED`; without a usable token, `DNS_TOKEN`; a token Cloudflare refuses, `DNS_AUTH`. Each says the step that fixes it, and the dashboard shows those steps in place of the records.
- **Caddy ignores `proxy.dns`.** It is read at every DNS request, left out of the settings digest generations record (every field in `CADDY_IGNORED_FIELDS` is), and never a pending proxy setting, so editing it needs no `rig proxy reload`.

## Considered

- **A separate token with DNS:Edit only for records.** Rejected: the owner asked to reuse the token, and its scope is already exactly the zone's DNS. A leak of either is the same takeover (ADR 0014, "What a leak can do").
- **The web calling Cloudflare.** Rejected: the browser and the Next.js server would need the token; rigd is the runtime authority and already owns it.
- **A dedicated `/v1/dns` route like the env editor's.** Rejected: DNS writes are Operations that belong in Activity, the queue and the CLI's progress, which `/v1/command` already gives.
- **Upsert by name and type in rigd.** Rejected: the CLI and the page plan against what they showed the owner, and send the record id and `modifiedOn`, so rigd's write is never a guess at which record was meant.

## Consequences

- The token's reach is unchanged, but now a dashboard session can rewrite the zone. The dashboard's admission (`docs/website.md`) is what stands between the Internet and that power, as it already does for deploys and secrets.
- Every page load of the Proxy page asks Cloudflare for the zones and records (two or more requests) and runs `tailscale ip -4`. Fine for one zone; `proxy.dns.zones` bounds it otherwise.
