# A forgotten Project's Tools stay installed, released to the next owner

## Problem

A Target publishes each Tool into `<RIG_ROOT>/bin`, shared by every Project, and records its ownership in `<RIG_ROOT>/installed/owners/<sha256(path)>.json`: the owning Target id, its names, and `revision`, the SHA-256 of the bytes it published. Only that Target may replace or retire the file; any other is refused with `ARTIFACT_CONFLICT`.

`rig forget` dropped the Project's records but left its Tools and their ownership records ([#343](https://github.com/b-relay/rig/issues/343)). The same repository registered again gets new Target ids, so its deploy was refused `ARTIFACT_CONFLICT` against a Target nothing records, for as long as the Rig root existed. It is the Tool form of #336, which ADR 0014 fixed for routes ("A block lives no longer than its Target").

## Decision

**`forget` leaves the files in place and changes nothing about them.** The write that drops the registration is what releases them: a Tool whose ownership record names a Target no state record names is _released_. Removing the files was rejected:

- A Tool is a command on the user's `PATH`. A forget is not Project deletion (see `CONTEXT.md`): it leaves the repository, the workspace and the data on disk, and a stale binary that still runs is a smaller surprise than a command that vanished.
- Rig's own Project publishes `rig` and `rigd`, and rigd's system job runs `<RIG_ROOT>/bin/rigd`. Removing it on a forget of that Project would leave launchd nothing to start after a crash or reboot.
- Nothing about the Tools changes before the state write, so nothing needs compensating when it fails, unlike a route withdrawal. A write that does not commit leaves the Project registered and its Tools owned; one that commits and then fails its directory sync is a completed forget (reported with #342's warning) and its Tools are released; a state that cannot be read back is `FORGET_UNCERTAIN`, and the Tools follow whichever the state says. The forget's warnings name the Tools left in `bin/`, and caution against deleting `bin/rigd`.

**The next Target that publishes at a released path takes it over**, from any Project, through the same checkpointed install as any publication (the old bytes and ownership record are backed up and restored by a rollback), replacing the file by atomic rename. The running process keeps its inode, so taking over `bin/rigd` is the same step an upgrade is. This needs no step from the user, so Hosts where an earlier forget already left Tools recover by themselves. One exception: a released `bin/rig` or `bin/rigd` goes only to a Target of the repository that published it, since launchd starts whatever `bin/rigd` holds and any repository may call itself `rig` (a Project name proves nothing). When Rig publishes either, it records the publishing repository's root commits: `git rev-list --max-parents=0 <deployed Commit>` in the Project's own registered repository, sorted; the same in every full clone, whatever its remotes. They are never read from Rig's mirror or a deployed checkout, whose history Rig fetches one Commit at a time and so can keep a shallow boundary the Project's repository no longer has. They are kept in `installed/owners/<sha256(path)>.repository.json`, beside the ownership record rather than in it, since older rigds read that record strictly. The file names the owner and revision it was written for, so one left from an earlier publication says nothing, and the effect checkpoint covers it like the record. A takeover compares it with the claimant's root commits, read the same way, and is refused `ARTIFACT_CONFLICT` (saying it is Rig itself, to keep it, and never to delete it) when they differ, when either is unknown, or when the executable was published before provenance was recorded: Rig fails closed, and such a Host upgrades Rig by the manual steps of the rig:rigd skill's upgrade reference. A recorded `rig` Target's own deploys are no takeover and work as before; its next publication, or its next start that finds the executable current, records provenance.

A shallow clone cannot prove its identity: git reports where its history was cut as its roots. Before reading roots, Rig asks the Project's repository `git rev-parse --is-shallow-repository`. A shallow one is never recorded as provenance (a recorded Target still publishes; it just records none), and its takeover is refused `ARTIFACT_CONFLICT` with reason `repository-shallow` and the hint to run `git fetch --unshallow` in the Project's repository, then deploy again; once it has, the next deploy reads its whole history there. A deployed Commit the Project's repository no longer holds is `repository-unknown`. Rig never fetches history by itself. (Reading the roots in Rig's mirror was tried first and rejected: a mirror cloned from a shallow repository keeps shallow boundaries that no fetch of single Commits, nor `--unshallow` from a repository that has since pruned the branch behind them, removes.) Releasing is decided at the one place every publication passes, `ArtifactOwnership.inspect`, from a reader of the recorded Target ids that rigd hands the effects adapter, so the provider holds no state. It is read only when another Target asks for a path, after the ownership record; every Target is recorded before it publishes a Tool (a deploy persists its candidate first, `up` its planned Target), so a Target being created is never taken for released. Absent a reader, nothing is released.

**Rig never replaces or removes bytes it did not publish.** A released Tool whose bytes differ from its recorded `revision` is refused with `ARTIFACT_CHANGED`, saying its Target no longer exists and to move or delete the file; a released Tool that is gone frees its path. A Target that retires a path it never owned (a Preview destroy, a superseded Tool) leaves a released Tool there alone and removes only its own receipt; a released Tool that changed blocks that retire with `ARTIFACT_CHANGED`, as an owned Tool edited by hand does.

**No automatic sweep removes released Tools.** A sweep like the route sweep would delete files on rigd start, including `bin/rigd` and `bin/rig` should a state file ever be lost. Doctor reports instead: `tool-owners` names every Tool in `bin/` whose owner Target is not recorded, with how each is recovered, and warns never to delete `bin/rig` or `bin/rigd`. Released Tools alone pass the check (`tool-orphaned`): they keep working and need nothing, and a forgotten Rig Project's `bin/rigd` must not leave doctor failing until someone deletes it. A changed one fails it (`tool-changed`), since it refuses every publication there until it is moved. The forget's warning names changed Tools apart, for the same reason. It reads the ownership records before the state, so a deploy in progress is never reported; a forget running meanwhile can be, once, as with `route-owners`.

## Threat model

As in ADR 0014: the revision check guards against a Tool edited by hand at rest and against a misconfiguration, not against the same user rewriting `<RIG_ROOT>/bin` while a publication is in flight (between the digest and the rename). That user can replace any file there directly. Repository provenance guards against registering an unrelated repository that happens to be named `rig`, not against a repository built deliberately from Rig's history; a root commit identifies a history, not who controls it.

**Recovery.** A takeover is an ordinary checkpointed install, so a rigd that dies in it (before or after the executable is renamed into place, or after its ownership record is written) is rolled back by its Target's recovery. Recovery and the claims rigd seeds at startup take an ownership record that is still byte for byte what the checkpoint captured as the change's own starting point, not as a Target that published there later; otherwise the released owner's record, still in place after the rename, would make recovery refuse (`EFFECTS_CHANGED`) and leave the new bytes installed.

## Consequences

- A forgotten Project's Tool name is free for any Project at once, while its file keeps working until then.
- Stale binaries can remain in `bin/` until a Target publishes the same name or the user deletes them; doctor keeps naming them.
- An ownership record whose file the user deleted stays on disk, unreported, until a Target publishes there. Its receipts stay too; nothing reads either.
